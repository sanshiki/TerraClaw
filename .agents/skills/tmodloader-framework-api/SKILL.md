# tModLoader Framework API

把第三方 Mod 视为不受控制的调用方。先定义稳定契约，再把 tModLoader 和业务实现隐藏在契约之后。

## 工作流

1. 阅读仓库的 `AGENTS.md`、目标代码及相邻公共 API，遵循现有命名空间和生命周期模式。
2. 判断功能是否会被第三方调用、实现、注册或监听。
3. 在修改前划定公共契约与内部实现边界。
4. 按需读取 [references/design-rules.md](references/design-rules.md)，尤其在设计 `Mod.Call`、Registry、事件或兼容升级时。
5. 实现最小、稳定的公共表面，并让内部代码依赖该契约。
6. 检查卸载、重复注册、非法输入、未初始化访问、多人同步和旧调用方兼容性。
7. 运行 `dotnet build`；提醒用户最终仍需在 tModLoader 中执行 Build + Reload 和游戏内验证。

## 决策规则

对每个新增对象依次判断：

- 第三方是否需要创建它？需要则定义公共接口。
- 第三方是否需要注册它？需要则提供 Registry 方法，不公开可变集合。
- 第三方是否需要监听它？需要则提供公共事件，不要求 Hook 内部方法。
- 第三方是否需要调用它？需要则放入专用 API 类，并通过 `Mod.Call` 暴露入口。
- 返回值是否泄露实现？若是，改为接口、DTO、只读集合或不可变快照。

若答案均为否，将实现保持在 `Internal` 命名空间或等价的内部边界中。

## 实施约束

- 使用 `XxxApi`、`IXxx`、`XxxRegistry` 和描述性事件名表达公共角色。
- 让 Registry 负责 ID 校验、去重、排序、生命周期以及需要时的网络同步。
- 仅允许外部注册、查询和读取；不要公开 `List<T>`、`Dictionary<TKey,TValue>` 或 `HashSet<T>`。
- 使用仅承载数据的 DTO，禁止从 API 返回内部存储、管理器、序列化器或网络处理器。
- 让 `Mod.Call` 只做参数验证、命令分派和 API 入口返回；不要在其中实现业务逻辑。
- 至少考虑 `GetAPI`、`GetVersion`、`HasFeature` 三种跨 Mod 调用。
- 在 `Load` 后建立 API，在 `Unload` 时解除事件、清空 Registry 和静态引用。
- 对未初始化或无效调用返回明确结果或抛出有语义的异常，禁止意外 `NullReferenceException`。
- 保留已经发布的方法签名和语义；新增能力使用新成员、重载或版本化能力探测。
- 不为“可能有用”而扩大公共 API。公共表面一旦发布就是兼容性承诺。

## 审查输出

审查现有代码时，优先报告会破坏第三方 Mod 的问题：

1. 可变内部集合或具体实现类型泄露。
2. API 生命周期、卸载清理或事件退订错误。
3. 已发布签名或语义的破坏性变更。
4. Registry 的重复、校验、同步或顺序行为不明确。
5. `Mod.Call` 参数处理不安全或包含业务逻辑。
6. 缺少针对公共契约和兼容行为的测试。

提供具体文件和行号，并给出保持旧调用方可用的修复方案。

## 完成检查

- 公共类型不依赖 `Internal` 类型。
- 所有暴露集合均为只读视图或快照。
- 第三方扩展点使用接口而非强制继承内部具体类。
- 事件订阅可在卸载时清理。
- `Mod.Call` 对空参数、未知命令和错误参数类型有确定行为。
- API 初始化时机明确，重载后不保留陈旧静态状态。
- 新功能可通过 `HasFeature` 或等价机制探测。
- 旧调用方式仍可编译并保持原语义。
